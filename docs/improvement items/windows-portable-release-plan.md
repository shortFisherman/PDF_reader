## 1. 如何使用这份清单

本清单用于跨会话连续实施，不要求一次完成全部事项。一次只处理一个编号；完成该编号的定向测试、完整验证、发行态验证、文档同步和提交后，再开始依赖它的下一项。

每项使用以下状态：

- `待处理`：尚未开始。
- `进行中`：已经建立独立变更并正在实施。
- `已改进`：风险已降低，但尚未完全满足验收标准；必须填写剩余问题。
- `已完成`：全部验收标准满足，并记录验证证据和完成提交。
- `暂缓`：当前明确不做，必须写明原因和重新评估条件。
- `不适用`：核验后确认不适用于当前发行形态，必须写明依据。

更新条目时，不要只勾选复选框。至少同时填写：

```markdown
- 状态：`已完成`
- 完成日期：YYYY-MM-DD
- 完成提交：`<commit>`
- 验证证据：`<命令、测试、干净机报告或产物路径>`
- 剩余问题：无 / <仍未解决的部分>
```

完成标准分为三层，不能相互代替：

1. **源码层**：路径、生命周期和禁止行为由代码强制，不只依赖 README 约定。
2. **发行层**：从最终 ZIP 解压后的程序运行测试，不以源码目录或开发虚拟环境代替。
3. **干净机层**：在没有 Python、Node.js、项目源码和既有模型缓存的 Windows 环境验证。

## 2. 已确认的产品与发行决策

下列内容是本计划的既定约束，后续会话不得在没有用户新决定时擅自改回开发者安装形态：

1. 首个正式发行目标为 Windows 10/11 x64 便携 ZIP。
2. 用户解压后只需双击顶层 `PDF Reader.exe`，不要求安装 Python、Node.js、Git 或运行 PowerShell 命令。
3. 使用 PyInstaller `onedir` 或经验证具有同等隔离能力的目录式打包；当前不追求 `onefile`。
4. Python 解释器和固定版本 Python 依赖在构建期随发行版提供；发行程序不得使用或修改系统 Python。
5. 正常启动和翻译过程不得执行 `pip install`、调用 `pip.exe`、`python -m pip`、`py.exe`，也不得联网下载 Python wheel。
6. 模型、字体等运行资源允许首次使用时按需下载，但所有程序自有可变数据必须保存在 EXE 所在便携目录的 `data/` 下。
7. 程序不得设置永久用户/系统环境变量，不得修改用户或系统 `PATH`，不得安装系统字体、Windows 服务、计划任务或开机启动项。
8. 便携目录不可写时必须在启动阶段明确失败；不得静默降级到 `%APPDATA%`、`%LOCALAPPDATA%`、用户主目录或系统临时目录。
9. 默认服务只监听 loopback；发行工作不得把默认地址改为 `0.0.0.0`。
10. 首次发行不包含自动更新、系统安装器、文件关联和 macOS/Linux 支持；这些内容只有在便携版稳定后经用户另行确认才进入范围。
11. 发行能力在当前仓库中以独立发行层实现，不复制或维护第二套业务源码；现有 `start.bat`、`python -m pdf_reader`、仓库 `venv/`、开发 `config.toml`、`cache/` 和 `logs/` 必须保持可用且不被发行构建修改。

“最好使用虚拟环境”的验收语义固定为：发行版必须使用自带、不可影响系统 Python 的隔离运行时。PyInstaller `onedir` 的私有解释器与依赖目录满足该目的，不要求首次启动再创建 `.venv`。若未来确实需要动态 Python 插件，每个插件必须使用便携目录内独立环境，并由用户显式触发；该能力不属于首版。

### 2.1 当前项目与发行层的边界

本计划采用“同一仓库、单一业务源码、独立发行层”结构。不能把当前项目完整复制到一个 `release/` 子目录后分别维护，因为两套源码会很快产生修复、测试、依赖与安全边界漂移。也不能把 PyInstaller 临时文件和发行依赖安装到仓库 `venv/`，否则会污染当前开发环境。

建议使用以下源码与产物边界：

```text
PDF_reader/
├─ src/pdf_reader/                 # 唯一业务实现；开发模式与发行模式共享
├─ static/                         # 唯一前端资源
├─ templates/                      # 唯一模板资源
├─ packaging/windows/              # 受版本控制的 Windows 发行专用层
│  ├─ README.md                    # 构建输入、输出、清理与排错说明
│  ├─ launcher/                    # 顶层启动器与服务包装入口
│  ├─ hooks/                       # 必要的 PyInstaller hooks
│  ├─ manifests/                   # Windows manifest、版本资源、依赖/许可证规则
│  ├─ pdf_reader.spec              # onedir 构建定义
│  └─ build.ps1                    # 唯一正式本地构建入口
├─ tests/release/                  # 发行模式与最终产物测试
├─ build/release-windows/          # 忽略：专用构建 venv、PyInstaller workpath、中间文件
└─ dist/release-windows/           # 忽略：解压目录、ZIP、校验和、manifest
```

其中 `packaging/windows/` 只存放发行适配和构建基础设施，不复制 `src/`、`static/`、`templates/` 或依赖 wheel。构建脚本从当前提交读取这些唯一来源，将结果写到已经被 Git 忽略的 `build/` 与 `dist/`。

现有源码可以为了支持显式的便携运行模式而修改，例如增加 `RuntimeLayout`、首次配置状态或服务入口；这些改动必须满足：

- 默认未启用便携模式时保持当前开发路径、CLI 和行为；
- 便携差异从入口显式注入，不在业务模块散布 `sys.frozen` 判断；
- 同一业务测试同时覆盖开发模式和发行模式；
- 构建脚本不写入、升级或删除根 `venv/`；
- 构建前后开发 `config.toml`、`cache/`、`logs/` 和 `venv/` 的路径、内容及文件元数据不因构建而改变；
- 清理发行产物只允许作用于已解析并验证的 `build/release-windows/` 与 `dist/release-windows/`，不得扩大到仓库根或用户数据。

## 3. 便携写入边界

### 3.1 目标目录布局

最终布局以构建验证后的实际产物为准，但职责必须保持如下分离：

```text
PDF Reader/
├─ PDF Reader.exe                 # 用户入口；保持真实用户环境，用于启动、打开浏览器和退出
├─ app/                           # 发行时生成的只读程序、私有 Python 运行时和固定依赖
│  ├─ PDF Reader Service.exe      # 受控环境中的本地服务（名称可在实现时调整）
│  ├─ _internal/
│  ├─ static/
│  ├─ templates/
│  ├─ config.example.toml
│  └─ licenses/
└─ data/                          # 首次启动创建；所有程序自有可变数据
   ├─ config/config.toml
   ├─ documents/
   ├─ models/
   ├─ fonts/
   ├─ upstream-cache/
   │  ├─ babeldoc/
   │  ├─ pdf2zh-next/
   │  ├─ huggingface/
   │  ├─ modelscope/
   │  └─ torch/
   ├─ temp/
   ├─ pycache/
   ├─ logs/
   └─ home/.cache/                # 接住第三方 Path.home() 硬编码路径
```

`PORTABLE_ROOT` 必须根据真实 EXE 所在目录解析，不能使用进程当前工作目录。快捷方式、PowerShell、资源管理器、带空格路径和中文路径启动时必须得到同一根目录。

### 3.2 必须留在便携目录内的内容

- PDF Reader 配置与 API Key 文件；
- 原 PDF 关联状态、译文 PDF、阅读进度、术语与候选数据；
- BabelDOC、pdf2zh-next、Hugging Face、ModelScope、Torch 等第三方缓存；
- 下载的版面分析模型、字体和资源元数据；
- 翻译缓存数据库；
- Python 字节码和可控的原生库缓存；
- PDF Reader 及受控子进程创建的临时文件；
- 主日志、任务日志、崩溃诊断和更新/迁移日志；
- 将来如获授权产生的插件环境和下载物。

### 3.3 明确不作“零系统痕迹”承诺的内容

Windows 和用户主动使用的默认浏览器仍可能在便携目录之外产生正常系统痕迹，例如 Defender/SmartScreen、Prefetch、事件日志、DNS 缓存、最近文件、浏览器历史与浏览器缓存。发行说明必须准确表述为“PDF Reader 自己管理的文件全部便携化”，不能声称整个操作系统运行前后字节级不变。

## 4. 长期发行红线

无论后续如何实现，以下规则必须始终成立：

1. 发行程序不探测、调用、升级或修改用户已安装的 Python、pip 和用户 `site-packages`。
2. 翻译任务不得安装 Python 包；Python 依赖只能在构建期由锁定清单进入发行物。
3. 所有程序自有写入必须位于规范化后的 `PORTABLE_ROOT/data` 内，路径穿越、符号链接或 junction 不能绕过边界。
4. 第三方包必须在其缓存路径常量首次求值或导入前收到受控环境；事后修改变量不算完成。
5. 启动器不得把虚拟 `HOME`/`USERPROFILE` 传给默认浏览器；浏览器应由保持真实用户环境的父启动器打开。
6. 便携目录不可写时快速失败，不在其他目录继续运行。
7. 覆盖升级不得覆盖现有 `data/`，数据迁移失败必须保留最后一个可用版本。
8. 服务继续只监听 loopback，并保持当前密钥脱敏、文档身份、任务互斥、事务写入与优雅关闭红线。
9. 发行 ZIP、校验和、源码标签、许可证与依赖清单必须能对应到同一个提交和依赖锁。
10. “源码测试通过”不能代替“最终 ZIP 在干净 Windows 上通过”。
11. 发行构建不得改写当前开发环境、开发配置或开发数据；便携模式改动不得取消或隐式改变现有开发启动方式。

## 5. 执行纪律

每个编号遵循以下流程：

1. 阅读本条目、`docs/architecture.md`、相关源码与现有测试；存在 `.codegraph/` 时先使用 CodeGraph 定位调用链。
2. 记录工作区和 HEAD 基线，避免覆盖用户已有修改。
3. 先写能表达发行不变量或复现外部写入的测试。
4. 实施满足当前便携版边界的最小改动，不顺手加入安装器、自动更新或跨平台支持。
5. 运行定向测试和 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1`。
6. 涉及打包的条目必须从最终 `dist`/ZIP 运行冒烟测试；不得从仓库 `venv` 运行来替代。
7. 当前实现事实变化时，同一变更更新 `docs/architecture.md`；用户使用方式变化时同步 README。
8. 更新本条目的状态、证据、提交和剩余问题，并向第 12 节追加完成记录。

发行构建还必须遵守以下隔离步骤：

1. 构建脚本创建并使用 `build/release-windows/venv` 等专用、可删除环境，不复用根 `venv/`。
2. PyInstaller 的 `workpath`、`distpath`、缓存、临时文件和日志均显式指向发行构建目录。
3. 构建开始前记录开发 `venv/`、`config.toml`、`cache/`、`logs/` 的存在状态与快照，结束后验证未改变。
4. 只读获取 `src/`、`static/`、`templates/`、锁文件和许可证作为构建输入。
5. 清理脚本先解析绝对目标并验证其严格位于两个发行输出目录内，不能使用未验证变量或宽泛递归删除。

以下做法禁止作为捷径：

- 为了通过审计而忽略、删除或放宽目录外写入检测；
- 通过永久修改用户环境变量重定向缓存；
- monkey patch 或复制/修改 pdf2zh-next、BabelDOC 上游源码来绕过其缓存路径；
- 把整个用户主目录视为允许写入区；
- 用“通常不会发生”代替首次下载、异常、取消和崩溃路径测试；
- 在 Release 构建中从网络获取未锁定或未校验哈希的 Python 包；
- 在同一个提交里同时完成打包、自动更新、安装器和大规模 UI 重写。

## 7. P0：便携隔离基础

### P0-01 固化便携根、目录布局与写入边界

- 状态：`已完成`
- 完成日期：2026-09-04
- 完成提交：`3cb07cb`（基线 `a4c0d64`）
- 验证证据：`tests/test_paths.py` 28 passed、1 conditional skip；受影响模块定向回归 431 passed、1 conditional skip；最终 `scripts/verify.ps1` 1508 passed、1 conditional skip，coverage policy（line 92.7%、branch 86.5%）、术语质量门、mypy、Ruff、ESLint 与全部前端测试通过
- 剩余问题：无；真实最终 EXE/ZIP 的长路径、ACL 与目录外写入复验按 P2-02 继续执行，不改变本条目源码层完成结论

#### 当前问题

当前 `paths.py` 使用项目标记查找资源根，并让数据根默认等于项目根；这适合源码仓库，但没有定义冻结 EXE、只读程序资源、用户可变数据和发行升级的边界。业务模块仍可能接收绝对缓存路径，第三方依赖也可能绕开项目路径策略。

#### 目标状态

- 明确区分 `RESOURCE_ROOT`、`PORTABLE_ROOT` 和 `DATA_ROOT`。
- 冻结运行时从 EXE 位置解析 `PORTABLE_ROOT`，源码开发模式保持可用且语义明确。
- 正式发行态强制 `DATA_ROOT = PORTABLE_ROOT/data`，不接受任意外部数据根覆盖。
- 所有写入路径在创建或替换文件前验证规范化目标位于数据根内。
- 符号链接、junction、`..`、大小写和不存在的尾部路径不能绕过边界。
- 启动时检查目录可写；失败时给出稳定错误码和用户可读消息。

#### 建议实施步骤

1. 新增可测试的运行模式与路径对象，不在各模块重复读取 `sys.frozen` 或环境变量。
2. 定义便携目录契约和创建顺序，确保 ZIP 本身不包含真实 `data/config/config.toml`。
3. 将配置、术语、文档缓存、日志和临时工作区接入统一数据路径。
4. 对绝对 `cache_dir` 的发行态语义作出明确决定：便携发行态应拒绝逃逸数据根的值。
5. 建立安全的 `is_within_data_root`/路径解析边界，覆盖 Windows junction 和符号链接。
6. 增加开发模式兼容测试以及冻结模式模拟测试。
7. 同步架构和配置参考文档。

#### 验收标准

- [x] 从中文、空格和长路径下启动时，便携根始终等于 EXE 所在目录。
- [x] 改变当前工作目录不会改变资源根或数据根。
- [x] 配置、日志、文档缓存和临时工作区全部落在 `data/`。
- [x] 发行态配置不能把缓存定向到便携目录之外。
- [x] junction、符号链接和路径穿越测试不能逃逸数据根。
- [x] 只读目录在导入翻译依赖前快速失败，且不写入回退目录。
- [x] 开发者当前启动和测试方式仍可工作。
- [x] 未启用便携模式时，现有 `start.bat`、`python -m pdf_reader`、配置位置和数据位置保持兼容。
