# PDF Reader 最小冻结版设计

## 背景

PDF Reader 是一个本地双语 PDF 阅读器。它使用 PDFMathTranslate-next 提供底层翻译能力，通过 Flask、PyMuPDF 和原生 JavaScript 实现按页或按范围翻译、双栏连续阅读、滚动对齐、翻译进度推送、术语累积和阅读位置恢复。

项目已经具备稳定的核心能力，但继续与 PDFMathTranslate-next WebUI、zotero-pdf2zh 和 Translate for Zotero 竞争整篇 PDF 翻译、模型数量或文献管理集成，投入产出比很低。当前决定进行一次最小收尾，然后冻结项目。

## 目标

冻结版的目标不是增加功能，而是让未来的维护者在十分钟内回答以下问题：

1. 项目解决什么问题，当前有哪些能力？
2. 如何安装、配置、启动和验证？
3. 项目为什么冻结，目前有哪些已知限制？
4. 如果恢复开发，应该从哪里开始？

## 范围

### 1. 修复已确认的可见乱码

- 检查启动页和底部工具栏中的中文文案。
- 修复确认存在的编码或文本损坏。
- 不调整布局、配色、交互结构或视觉风格。

### 2. 建立统一验证入口

- 保留 Python 全量测试、Ruff 检查和 Ruff 格式检查。
- 将当前正式前端回归测试纳入统一命令。
- 区分正式回归测试与历史 TDD RED 复现脚本；历史脚本可以保留，但不得让维护者误以为它们属于应当全部通过的测试套件。
- README 中只记录稳定验证命令，不硬编码容易过期的测试数量。

### 3. 更新项目入口文档

README 应准确说明：

- 项目的用途和本地单用户定位。
- 当前核心功能及其边界。
- 安装、配置、启动和验证步骤。
- PDFMathTranslate-next 是底层依赖，而不是本项目自研翻译引擎。
- 项目已经冻结：不主动增加功能，仅考虑安全问题、数据损坏或无法启动等严重缺陷。
- 指向项目状态文档。

### 4. 新增项目状态文档

新增一份简短的状态文档，至少包括：

- 冻结日期和冻结原因。
- 当前架构及关键代码入口。
- 已知产品与技术限制。
- 上游 PDFMathTranslate-next 使用 AGPL-3.0 的授权提醒；该文档只提示风险，不给出法律结论，也不在本次收尾中执行重新授权。
- 恢复开发时的推荐起点。

### 5. 最终验证和仓库卫生

- 运行统一验证入口，并分别确认 Python 测试、前端测试、Lint 和格式检查结果。
- 确认配置密钥、缓存、日志和临时文件未被提交。
- 确认工作区只包含本次冻结收尾所需变更。

## 明确不做

本次冻结不包含：

- PDF.js 文本层、文本选择、搜索、高亮或批注。
- AI 问答、段落解释、知识库或笔记系统。
- 翻译任务队列、暂停、取消或断点续传。
- 多用户、多文档并发或云服务部署。
- Zotero 插件、移动端或浏览器扩展。
- Windows EXE、安装器、一键打包或正式 Release。
- 新模型供应商、OCR 能力或翻译质量优化。
- 大规模重构、依赖升级或许可证变更。

## 实施边界

- 优先修改文档、测试入口和已确认损坏的文案。
- 不改变翻译流程、缓存格式、API 协议或 PDF 输出。
- 如果统一验证暴露真实业务回归，只修复阻止冻结版正常运行的问题；其他问题记录到状态文档。
- 不为了提高测试数字新增低价值测试。

## 验收标准

冻结版完成时必须满足：

1. 启动页和工具栏不存在已确认的乱码文案。
2. 一个统一命令可以运行所有正式前端回归测试。
3. README 提供有效的安装、启动和验证步骤，并明确冻结状态。
4. 项目状态文档解释冻结原因、架构入口、已知限制和恢复建议。
5. Python 全量测试、正式前端测试、Ruff 检查和格式检查全部通过。
6. 没有缓存、密钥、日志或临时测试文件进入提交。

## 恢复开发建议

如果未来恢复开发，先验证真实用户需求，不继续扩充整篇 PDF 翻译能力。优先评估基于 PDF.js 文本层的选择、搜索、段落翻译和双语笔记闭环；PDFMathTranslate-next 继续作为可选的整页翻译与导出能力。
