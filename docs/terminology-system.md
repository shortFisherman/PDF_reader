# 术语提取与翻译控制指南

这套术语系统的目标不是让模型自动替用户决定译法，而是让模型帮助发现术语、由用户
作出最终决定，并让正文翻译持续遵守这个决定。

如果只记住三件事：

1. 候选术语只是建议，不会自动影响正文。
2. 手工新建或明确接受后的术语才是权威术语。
3. 修改术语只影响后续翻译；已经翻译的页面需要主动重译。

## 一、几个名称分别是什么意思

| 名称 | 含义 | 会不会影响正文 |
|---|---|---|
| 候选术语 | 候选模型从源文中发现的 `source → target` 建议 | 不会 |
| 已接受候选 | 用户在候选页选择或输入 target 后点击“接受”的词条 | 会 |
| 已拒绝候选 | 用户不希望继续看到提醒的候选；后台仍可累计观察统计 | 不会 |
| 文档用户术语 | 用户在当前 PDF 的“权威术语”页手工新建或导入的词条 | 会 |
| 全局术语 | 手工维护在 `docs/glossary.csv` 中、供所有 PDF 使用的默认词条 | 会，但可被文档词条覆盖 |
| 锁定术语 | 禁止误编辑、误拒绝或误删除的权威词条 | 与未锁定时优先级相同 |
| 有效词表 | 每次翻译前由系统从所有权威来源编译出的只读词表 | 会 |
| 权威术语块 | 从本次源文实际命中的有效词条临时生成的一段强制提示词 | 会；它不是磁盘文件 |

“观察次数更多”只用于帮助排序和判断，不会自动把候选升级为权威术语。最终采用哪个
target，始终由用户决定。

## 二、一次翻译实际经过什么流程

```text
┌──────────────────────────────────────────────┐
│ 1. 读取已有决定                              │
│    文档用户术语 + 已接受候选 + 全局术语      │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ 2. 编译 effective_glossary.csv               │
│    并从本次源文中找出实际出现的权威术语      │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ 3. 候选提取模型调用                          │
│    只提出建议，结果暂存在内存                │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ 4. 正文翻译模型调用                          │
│    使用步骤 2 已冻结的有效词表和权威术语块   │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ 5. 检查译文是否遵守本次活跃权威术语          │
│    首次不合规时，最多重试一次                │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ 6. 正文通过后写入 right.pdf                  │
│    然后才把步骤 3 的候选观察写入候选存储     │
└──────────────────────────────────────────────┘
```

候选提取虽然发生在正文模型调用之前，但两次调用彼此独立：步骤 3 的新候选不会进入
步骤 4，因此不会影响同一次翻译。只有正文验证并提交成功后，候选才会保存；正文失败、
取消或术语合规失败时，内存中的候选不会落盘。

## 三、普通用户怎么用

### 1. 翻译前固定关键术语

如果你已经知道某些词必须怎样翻译，最好在第一次翻译前设置：

1. 打开 PDF。
2. 点击阅读页工具栏中的“术语”。
3. 留在“权威术语”页，点击“新建术语”。
4. 在 `Source` 中填写原词，在 `Target` 中填写指定译法。
5. 可填写备注；不希望误改时勾选“创建后锁定”。
6. 点击“保存”，再开始翻译。

例如，提前创建 `Agent` → `智能体`，之后源文中实际出现 `Agent` 的翻译任务就会使用
这条约束。

### 2. 让系统自动发现术语

正常翻译单页、页码范围或全文即可。候选模型会从本次源文中提出建议，并经过本地过滤：

- source 必须能在实际送给模型的源文中找到；
- 普通词、结构异常条目和明显幻觉会被过滤；
- 保留的候选会记录实际命中页码、证据片段和观察次数。

候选提取失败不会阻止正文翻译；它只表示本次没有新增候选。

### 3. 审核候选

打开“术语”→“候选术语”：

- 下拉框列出模型提出过的 target，以及观察次数和覆盖页数；
- 文本框允许直接输入你自己的 target，不必接受模型原文；
- 展开证据可以查看该建议在哪些页、什么上下文中出现；
- 点击“接受”后，这个 source 和你选定的 target 才会进入权威体系；
- 点击“拒绝”后，它不会影响正文，也不会继续作为待处理项反复打扰你；后台仍可保留
  新观察，用于统计和以后重新判断。

### 4. 修改已经接受的译法

已接受候选会同时显示在“权威术语”页。要修改它：

1. 在“权威术语”中点击该词条的“查看候选”，或切换到“候选术语”并搜索 source。
2. 选择另一个建议，或在文本框中输入新 target。
3. 点击“更新接受译法”。

如果词条已锁定，先在“权威术语”页解锁。锁定的作用是防止用户操作误改，不是提高
模型中的翻译优先级。

### 5. 让新决定应用到已经翻译的页面

术语修改不会追溯重写 `right.pdf`。请重新翻译受影响的单页或范围，系统会在新任务开始
前重新编译有效词表，并用最新决定替换这些页面。

## 四、多个译法打架时怎么办

系统按规范化后的 source 聚合候选：忽略英文大小写差异，并把连续空白视为一个空格。
因此 `Agent` 和 `agent` 会被视为同一个 source；单复数、连字符变化、缩写和全称不会
被自动合并。

以 `Agent` 为例：

### 情况 A：两个译法都还没接受

第一次观察到 `Agent` → `智能体`，后来又观察到 `Agent` → `代理`，系统会把它们放在
同一个候选条目下：

```text
Agent
├─ 智能体：观察次数、覆盖页数、证据
└─ 代理：观察次数、覆盖页数、证据
```

系统会按不同页覆盖数、观察次数和稳定字典序给出推荐，但推荐不是权威决定。你可以选择
“智能体”、选择“代理”，也可以输入第三种译法，然后点击“接受”。在此之前，两种建议
都不会影响正文。

### 情况 B：已经接受“智能体”，后来模型又建议“代理”

新建议仍可作为观察记录追加，但 `accepted_target` 保持“智能体”，不会被模型改写。
有效词表继续使用 `Agent` → `智能体`。只有用户主动点击“更新接受译法”，它才会改成
“代理”。

### 情况 C：文档用户术语与候选或全局词表冲突

正文使用固定优先级：

```text
当前文档手工新建或导入的用户术语
                  ↓ 覆盖
当前文档中已接受的候选
                  ↓ 覆盖
全局 docs/glossary.csv
```

所以，如果全局默认是 `Agent` → `代理`，但这本 PDF 要求 `Agent` → `智能体`，直接在
当前文档中新建 `Agent` → `智能体` 即可。面板会把较低优先级的同名词条标记为
“被更高优先级覆盖”。

同一优先级如果存在无法确定解决的冲突，系统会拒绝编译，避免按文件顺序或首次出现静默
选一个译法。

## 五、到底有什么内容会传给模型

有两类独立的模型请求。

### 候选提取模型

候选请求接收：

- 候选提取系统提示词；
- 本次页面或批次的源文本，最多取 `[term_extraction].max_input_chars` 个字符。

当前实现不会把 `effective_glossary.csv`、已有候选表或此前已拒绝的译法传给候选模型。
因此模型以后仍可能再次建议一个已有 source 的不同 target。冲突不会丢失，也不会覆盖
用户决定，而是由候选存储聚合成多个可选 target。

### 正文翻译模型

正文请求使用的是候选调用开始前就已冻结的权威结果：

1. 非空的完整 `effective_glossary.csv` 通过上游支持的 `glossaries` 设置交给正文翻译；
2. 系统再从本次源文中筛出实际出现的权威词条，动态生成“权威术语约束”并追加到正文
   系统 Prompt，作为第二道约束。

所以，传给正文的并不只有一个 CSV 文件，但两种输入来自同一套权威数据。“权威术语块”
没有单独文件，只存在于这一次正文请求的内存上下文中；未在本次源文命中的词条不会进入
这个动态块，仍保留在有效词表中交给上游处理。

正文产出后，系统还会检查本次实际命中的权威 target 是否出现在译文中；第一次不合规时
最多重试一次。重试仍不合规则不提交该次译文。

## 六、Token 和费用

启用候选提取后，只要本次源文可提取且 Provider 受支持，通常会为每个翻译任务增加一次
独立的模型请求；遇到可重试错误时还可能按配置重试。因此它会增加输入、输出 Token、
等待时间和费用。实际增量取决于本次源文长度、候选提示词、模型计费和重试情况。

控制方法：

- 不需要继续发现新术语时，把 `[term_extraction].enabled` 设为 `false`；已经确认的权威
  术语仍会继续约束正文。
- 用 `max_input_chars` 限制候选请求的最大源文字符数；它限制的是字符，不是精确 Token。
- 候选请求的 `qps`、`max_workers`、`timeout` 和 `retry_count` 与正文配置相互独立。
- 自定义候选 `prompt` 越长，也会增加候选请求的输入 Token。
- 存在活跃权威术语时，正文还会增加动态约束块的少量输入 Token；只加入本次实际命中的
  词条，并有字节上限。

候选提取支持 `deepseek`、`openai` 和 `openai_compatible`。使用其他 Provider 时，候选
提取会安全降级为 unsupported，但手工术语、已接受术语和正文严格约束仍可继续工作。

## 七、候选提取配置

普通用户可以保持默认值。需要控制费用或等待时间时，在 `config.toml` 中配置：

```toml
[term_extraction]
enabled = true
# timeout = 30.0
# qps = 2
# max_workers = 1
# retry_count = 1
# max_input_chars = 80000
# prompt = "你是 PDF 领域术语提取助手……"
```

字段的类型、范围、默认值和重试边界以 [config.example.toml](../config.example.toml) 为准。
旧的 `translation.auto_extract_glossary`、`translation.term_qps` 和
`translation.term_pool_max_workers` 只为 1.x 配置兼容保留，不建议用于新配置。

正文严格术语约束没有关闭开关。`term_extraction.enabled = false` 只关闭新候选发现，不会
让正文忽略已有权威术语。

## 八、导入、导出和全局词表

### 当前文档的 CSV 导入与导出

术语面板可以导出当前文档的用户权威术语，格式为：

```csv
source,target,locked,note
Agent,智能体,true,本书统一译法
```

导入时可以只提供 `source,target` 两列。当前限制为文件最多 1 MiB、最多 1000 行；任一
坏行、批内重复或与当前文档已有 source 冲突都会整批拒绝，不会只导入一半。导入和导出
只操作当前 PDF 的用户术语，不会修改候选记录、其他 PDF 或全局词表。

### 全局词表

`docs/glossary.csv` 是所有 PDF 共用的全局默认词表，格式为：

```csv
source,target
Agent,智能体
```

全局词表在术语面板中只读显示。如需维护，建议停止服务后手工编辑该文件，并保持
表头和 CSV 格式正确。只对某一本 PDF 有效的译法，应优先在该文档的术语面板中创建。

## 九、文件分别存在哪里

| 文件 | 角色 | 是否需要备份 | 是否建议手工编辑 |
|---|---|---|---|
| `docs/glossary.csv` | 全局手工权威术语 | 是 | 可以，面板只读 |
| `cache/<hash>/user_glossary.csv` | 当前 PDF 的用户权威术语 | 是 | 否，优先用面板或导入 |
| `cache/<hash>/term_candidates.json` | 候选、接受/拒绝/锁定状态和观察统计 | 是 | 否 |
| `cache/<hash>/effective_glossary.csv` | 每次翻译前生成的有效词表 | 否，可重建 | 不要编辑 |
| `cache/<hash>/effective_glossary.meta.json` | 有效词表来源摘要和一致性校验信息 | 否，可重建 | 不要编辑 |
| `cache/<hash>/cumulative_glossary.csv` | 旧版累计术语表，历史输入 | 迁移完成前保留 | 不要并入权威文件 |
| `cache/<hash>/cumulative_glossary.csv.bak` | 首次迁移旧累计表时保留的恢复副本 | 建议保留 | 不要覆盖 |

`<hash>` 是源 PDF 的 SHA-256 小写十六进制摘要。同一个 PDF 只有放回对应的哈希目录，
应用才能把这些术语数据识别为该文档的数据。

应用按原子文件边界写入术语数据，但不会自动替用户备份。恢复时建议：

1. 停止服务，避免应用与复制操作同时写文件。
2. 先把当前文件移到一旁，再整文件复制备份，不要复制 `.tmp` 文件。
3. 保持原文件名和 `cache/<hash>/` 目录不变。
4. 启动后打开原 PDF，在术语面板中确认权威术语和候选状态。

最方便的跨环境迁移方式通常是从面板“导出 CSV”，再在目标环境为对应 PDF “导入
CSV”。如果需要连同候选观察、拒绝状态和锁定状态一起迁移，再备份整个对应的哈希目录。

## 十、常见问题和故障处理

### 接受或修改后，当前译文为什么没有变化

术语决定不会追溯修改已提交页面。请主动重译相关单页或范围。

### 为什么同一个 source 又出现了另一个 target

候选模型当前不会读取已有候选或有效词表，所以可以提出不同建议。系统会合并观察但不会
覆盖 accepted target；在候选页确认或更新即可。

### 为什么没有出现新候选

可能原因包括：候选提取已关闭、Provider 不支持、源 PDF 没有可提取文本、模型没有返回
候选、候选被本地规则过滤，或者请求超时/失败。候选失败不会让正文翻译失败；可查看
`logs/pdf_reader.log` 中不含正文和术语原文的安全摘要。

### `glossary_compliance_failed` 是什么

正文没有满足本次活跃权威术语，自动重试一次后仍未通过。系统为避免把违规结果写入
`right.pdf`，拒绝了这次提交。可检查 target 是否过于严格、是否适合当前语境，调整后重译。

### `glossary_verification_unavailable` 是什么

系统无法可靠提取源文或译文来完成合规检查，例如扫描型或无文本层 PDF。只要本次存在
需要检查的权威术语，系统会保守地拒绝提交，而不是假装已经遵守。当前项目没有 OCR
流程；可先确认该 PDF 是否包含可提取文本，或在不适用的情况下调整相关权威术语。

### 可以直接编辑 `effective_glossary.csv` 吗

不可以。它是可重建产物，下次编译会被覆盖。请在术语面板中修改文档术语或已接受候选，
或者维护全局 `docs/glossary.csv`。

## 十一、当前边界

- 候选提取模型不知道以前的候选、接受或拒绝结果，因此可能反复提出相同或冲突的建议；
  存储和优先级规则保证这些建议不能自动改写用户决定。
- 当前严格匹配面向可提取文本的英文 PDF → 中文翻译：source 匹配忽略大小写和连续空白，
  不自动推断单复数、连字符、缩写与全称是同一个词。
- target 合规检查以规范化后的精确目标译法为主，语义相同但字形或标点不同也可能被判为
  不合规。
- 批量翻译存在任一活跃术语不合规时，会对整个批次进行一次有界重试。
- 系统能提高术语一致性，但不能保证任意模型、任意 PDF 的输出绝对可靠；合规检查是正文
  写入前的第二道保护。

面向开发和维护者的当前架构事实见 [architecture.md](architecture.md)；上游边界决策见
[glossary-upstream-boundary.md](governance/glossary-upstream-boundary.md) 和
[term-extraction-client-boundary.md](governance/term-extraction-client-boundary.md)。
