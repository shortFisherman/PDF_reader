> 本文档记录“长期术语记忆、用户最终决定、正文翻译必须遵守用户术语”的产品与工程改进，不自动授权一次性实施全部事项。
>
> 建立日期：2026-08-31  
> 审计基线：`5bf10ea`  
> 适用上游：`pdf2zh-next 2.9.0` / `BabelDOC 0.6.2`  
> 当前主要场景：英文 PDF 翻译为中文  
> 核心边界：不修改、fork、vendor、复制、Monkey-patch 或 import-shadow 上游源码；所有改进只在本项目自己的适配层、术语存储层、任务编排层、前端和测试中完成。

## 1. 如何使用这份清单

本清单是长期执行台账，不是要求一次性完成的重构计划。后续会话一次只领取一个编号；完成该编号的测试、实现、文档和验证后，再开始下一个编号。

每项使用以下状态：

- `待处理`：尚未开始。
- `进行中`：已经建立独立变更并正在实施。
- `已改进`：风险已降低，但尚未满足该项全部验收标准；必须填写“剩余问题”。
- `已完成`：全部验收标准满足，并记录验证证据和完成提交。
- `暂缓`：当前明确不做，必须写明原因和重新评估条件。
- `不适用`：经核验确认不适用于当前项目，必须写明依据。

更新条目时，不要只修改复选框。至少同时填写：

```markdown
- 状态：`已完成`
- 完成日期：YYYY-MM-DD
- 完成提交：`<commit>`
- 验证证据：`<测试名称、执行命令或报告路径>`
- 剩余问题：无 / <仍未解决的部分>
```

`已改进` 与 `已完成` 的区别：

- 如果只是把术语附加到 Prompt，但没有证明正文翻译请求实际携带它，只能标记为 `已改进`。
- 如果只是新增前端提醒，而服务端仍会把未审核候选词自动用于正文，只能标记为 `已改进`。
- 如果用户定义的术语可能被自动候选覆盖、遗漏或静默忽略，相关 P0 条目不能标记为 `已完成`。
- 只有服务端最终翻译边界存在强制检查、违反时不会静默提交错误译文，并有失败路径回归测试，才能宣称“必须遵守”已经完成。
- 测试数量增加不等于完成；测试必须覆盖每个条目列出的产品不变量和失败场景。

## 2. 产品目标与术语语义

### 2.1 最终产品目标

术语系统最终必须成为由本项目持有的长期记忆，而不是上游一次性自动提取结果的被动缓存：

1. 用户可以定义 `source → target`。
2. 用户定义或确认后，该映射成为“权威术语”。
3. 只要源术语出现在待翻译文本中，正文翻译必须使用权威目标译法。
4. 自动提取只能产生“候选术语”，不能在未经用户确认时覆盖权威术语。
5. 用户可以查看、编辑、接受、拒绝、删除和锁定候选。
6. 系统应长期记住用户决定；模型、Prompt 或上游版本变化不能静默改写该决定。
7. 普通词、上下文短语和模型幻觉应尽量在进入候选池前被过滤；即使进入候选池，也不得自动污染权威词表。

### 2.2 术语分类

后续实现和测试统一使用以下概念，避免继续把所有 CSV 行都称为“累计术语”：

| 类型 | 含义 | 是否可直接约束正文 | 谁能改变 |
|---|---|---:|---|
| 权威术语（authoritative term） | 用户手工创建，或用户明确接受/编辑后的映射 | 是，必须 | 仅用户操作或显式导入 |
| 锁定术语（locked term） | 用户要求长期保持、不允许自动流程改变的权威术语 | 是，最高优先级 | 仅用户解锁后修改 |
| 候选术语（candidate term） | 自动提取器提出但用户尚未确认的映射 | 否 | 自动提取可追加观察，用户可处理 |
| 已拒绝候选（rejected candidate） | 用户判断不是术语或译法不应采用 | 否，且不应反复提示 | 用户可恢复 |
| 有效词表（effective glossary） | 为一次正文翻译编译出的只读权威术语集合 | 是 | 由项目根据确定性优先级生成 |

“自动提取次数多”不能自动把候选升级为权威术语。频率和投票只能帮助排序和推荐，最终决定仍属于用户。

### 2.3 “必须遵守”的可测试定义

对于当前主要场景——可提取文本的英文 PDF 翻译为中文——“必须遵守用户术语”至少意味着：

1. 本项目使用自己的边界匹配器确认源术语出现在当前输入页或批次中。
2. 本次翻译使用的有效词表中存在该术语及用户指定目标译法。
3. 正文翻译配置经过契约测试证明会把有效词表直接提供给正文翻译，而不是先要求自动提取模型重新复述。
4. 权威术语同时作为本项目追加的、只包含当前活跃词条的约束提示进入正文翻译，作为第二道防线。
5. 翻译结果在写入 `right.pdf` 前执行合规检查；能可靠提取译文文本时，必须确认指定目标译法出现且没有已知冲突译法。
6. 合规检查失败时允许有界重试；重试仍失败则任务返回明确的术语违规错误，不得把已知违规译文静默提交为成功。
7. 对扫描件、异常字体或无法可靠提取译文文本的页面，系统必须报告“无法验证”，不能伪称已验证遵守。

本定义不要求本项目重写 PDF 排版或修改上游翻译内部实现；约束、验证、重试和最终提交门位于本项目自己的调用边界。

## 3. 长期红线

无论后续如何实现，下列红线必须始终成立：

1. **不修改上游。** 不编辑 `venv/site-packages`，不维护 pdf2zh-next/BabelDOC fork，不复制其内部模块进本仓库，不在运行时替换上游函数或类，不创建同名包遮蔽真实依赖。
2. **用户决定优先。** 自动提取、自动投票、模型建议和历史首次结果都不能覆盖用户定义、确认或锁定的映射。
3. **候选与权威隔离。** 未经用户确认的候选不得进入正文有效词表。
4. **不静默违反。** 已知存在权威术语而译文未遵守时，不能仍以普通成功状态写回。
5. **不静默丢决定。** 迁移、崩溃、并发写入或上游升级失败后，最后一个有效的用户术语版本仍然可读。
6. **不把首次结果当真理。** 自动结果不得因为最先写入就永久锁死；自动观察只能更新候选统计。
7. **不让普通词无限污染。** 候选池和有效词表都必须有确定的过滤、状态与容量/分页边界。
8. **保持既有工程红线。** 文档身份、单任务互斥、后台 worker 所有权、PDF/术语原子提交和干净环境验证继续成立。

如果某个目标在当前上游公开/受支持配置下无法实现，处理顺序固定为：

```text
先用契约测试证明限制
  → 在本项目边界增加适配或独立服务
  → 必要时暂时关闭该上游功能
  → 记录剩余问题
```

不得把“直接修改上游内部代码”作为备选方案。

## 4. 明确不做与暂缓事项

以下内容不属于本轮主线，不能借术语优化顺手扩张：

- 不修改、fork、vendor 或 Monkey-patch pdf2zh-next/BabelDOC。
- 不重写 BabelDOC 的 PDF 解析、布局、字体或排版重建。
- 不为了术语系统把 Flask 改成其他后端框架。
- 不为了术语元数据直接引入 Redis、Celery、消息队列或远程数据库。
- 不把原生前端整体重写成 React/Vue。
- 不要求自动候选未经用户确认就影响正文翻译。
- 不把“自动生成更多词”当作质量提升目标；优先减少错误和普通词。
- 不把英文→中文之后切换日文、俄文等跨目标语言作为当前验收场景；跨语言命名空间和迁移暂缓，除非未来真实需求改变。
- 不在本清单内解决上游许可证、发布或网络部署问题；继续遵循现有治理文档。

当前只保证英文→中文主场景。若未来出现真实跨语言需求，应新建立独立条目，而不是扩张本清单现有验收范围。

## 5. 执行纪律

每个编号建议使用同一流程：

1. 确认工作区状态，记录当前基线和相关上游固定版本。
2. 每个编号启动一个全新的独立子 Agent；该 Agent 只处理当前编号，完成后关闭，不复用于下一个编号。
3. 主 Agent 负责总体设计、审查子 Agent 改动、集成、补强验证和更新台账；不得把多个编号打包交给同一子 Agent。
4. 只处理一个编号，不混入其他编号的实现。
5. 先写能复现当前风险或表达目标不变量的测试。
6. 对涉及上游行为的事项，先用离线契约测试固定观察到的行为，不凭文档或记忆猜测。
7. 实施满足本机、单用户、单活动文档边界的最小方案。
8. 不修改 `venv/`、全局 site-packages 或任何上游安装文件。
9. 运行条目定向测试，再运行：

   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts/verify.ps1
   ```

10. 若修改当前架构事实，同一变更更新 `docs/architecture.md`。
11. 若修改长期产品意图，先核对 `docs/project.md`；本清单本身不自动改写长期意图。
12. 在本清单条目中记录状态、提交、验证证据和剩余问题。

禁止以下“看似捷径”的实现：

- 在启动时给 `AutomaticTermExtractor` 或 `get_glossaries_for_translation` 赋新函数。
- 把上游某个 `.py` 复制到 `src/pdf_reader/` 后修改。
- 在仓库创建 `pdf2zh_next/` 或 `babeldoc/` 同名包覆盖安装依赖。
- 直接修改 `venv/Lib/site-packages` 后只在本机验证。
- 只靠更长 Prompt 宣称“用户术语必定遵守”，却没有配置契约和结果验证。
- 把现有 `cumulative_glossary.csv` 的所有行直接视为用户已确认。
- 自动重写用户词条，事后再让用户发现。

## 7. P0：用户术语正确性主线

### P0-01 固定现有上游术语行为与“不修改上游”契约

- 状态：`已完成`
- 完成日期：2026-08-31
- 完成提交：`38076cf`
- 验证证据：定向契约/治理/文档测试 41 passed；`scripts/verify.ps1` 全绿（818 Python tests，覆盖率、Mypy、ESLint 与前端测试全部通过）。
- 剩余问题：本项只固定上游限制与治理边界；用户权威术语尚未通过严格正文路径强制执行，由 P0-04 解决。

#### 当前问题

当前项目把 `docs/glossary.csv` 和每文档 `cumulative_glossary.csv` 传给上游。固定版本中，开启自动提取时，用户/累计词表主要先作为自动提取参考，正文翻译阶段只选择本次自动词表；关闭自动提取时，用户词表才直接进入正文词表。现有测试固定了字段和文件路径，却没有固定这一决定性语义。

如果不先写契约测试，后续会话可能误以为“传入 glossaries 就等于正文必用”，或为了修复而直接修改上游内部函数。

#### 目标状态

- 用离线、确定性的测试固定当前固定版本在 auto-on/auto-off 下的真实词表选择行为。
- 明确项目只依赖受支持的设置和输出契约，不依赖运行时替换上游内部函数。
- 用稳定通过的特征测试证明当前限制：“开启上游自动提取后，未被提取器复述的用户权威术语不会进入正文词表”。
- 形成一份简短的本地适配决策记录，说明 P0-04 为什么选择项目边界方案。

#### 建议实施步骤

1. 扩展 `tests/test_upstream_contract.py`，构造人工 glossary 与自动 glossary，分别验证 `auto_extract_glossary=True/False` 的正文选择结果。
2. 测试 `build_settings()` 当前传入的 `no_auto_extract_glossary`、`save_auto_extracted_glossary` 和 `glossaries` 组合。
3. 增加一个正向固定当前限制的特征测试：auto-on 且提取器漏掉人工术语时，人工术语未直接到达正文；不把预期失败长期留在测试基线中。
4. 在 `docs/governance/` 或本清单条目中记录可选方案：严格正文路径关闭上游自动提取；自动候选改由项目侧独立执行。
5. 增加仓库结构性守卫，拒绝被跟踪的 `pdf2zh_next/`、`babeldoc/` 影子包、上游源码副本或项目启动期 Monkey-patch 模块。
6. 不运行真实 API，不修改 site-packages；全部测试使用受控 fake 或固定数据对象。

#### 验收标准

- [x] auto-on/auto-off 的词表选择行为有离线契约测试。
- [x] 测试明确证明当前 auto-on 不能满足“用户术语直接约束正文”。
- [x] 记录了不修改上游的适配决策和允许使用的公开边界。
- [x] 仓库不存在上游源码副本、同名影子包或运行时 Monkey-patch。
- [x] 上游固定版本契约测试与完整验证通过。

### P0-02 建立权威术语、候选术语与安全迁移模型

- 状态：`已完成`
- 完成日期：2026-08-31
- 完成提交：`b9a2de2`
- 验证证据：定向测试 158 passed；`scripts/verify.ps1` 全绿（946 Python tests，line 93.6% / branch 86.7%，Mypy、Ruff、ESLint 与前端测试全部通过）；新增文件进入 Git 索引后 secret-scan 通过。
- 剩余问题：本项提供服务层模型、原子存储与幂等迁移，但尚未在打开文档时自动迁移，也尚未编译/接入正文有效词表；分别由后续 P0-03、P0-04/P1-01 接线。兼容期内旧累计 CSV 仍由现有上游流程维护。

#### 当前问题

`cumulative_glossary.csv` 同时承担自动结果、历史记忆和正文词表三种角色，只有 `source,target` 两列，无法表达：

- 这是用户定义还是模型生成；
- 用户是否确认、拒绝或锁定；
- 一个译法被观察多少次；
- 证据来自哪些页；
- 冲突译法有哪些；
- 是否允许自动流程修改。

现有所有行都由自动流程产生，不能在迁移时静默当成用户已确认。

#### 目标状态

采用项目自有、可原子提交的最小数据模型，把“用户决定”和“模型候选”分开。首选设计可在实施前通过小型 ADR 最终确定，但必须满足：

```text
docs/glossary.csv                         全局用户权威术语（保留现有入口）
cache/<pdf_hash>/user_glossary.csv        当前文档用户权威术语
cache/<pdf_hash>/term_candidates.json     自动候选、观察次数、证据和状态
cache/<pdf_hash>/effective_glossary.csv   确定性编译产物，不由用户直接编辑
```

如最终选择不同文件名或单一版本化 JSON，也必须保持同样的语义隔离和可导出 CSV 边界；不要仅为了元数据引入远程数据库或服务。

#### 最小字段

候选记录至少保存：

- 原始 source；
- 规范化 source key；
- 一个或多个 target 建议及各自观察次数；
- 出现页码；
- 有界原文证据片段；
- 状态：`candidate` / `rejected` / `accepted`；

## 10. 目标架构摘要

全部主线完成后的职责边界应为：

```text
┌──────────────────────────────────────────────────────────────┐
│ PDF Reader 项目自身                                          │
│                                                              │
│  用户术语 API/UI ──→ 权威术语存储 ──→ effective glossary     │
│         ↑                       │                             │
│         │                       ├─→ 活跃词条约束 Prompt       │
│  候选审核界面                  └─→ 正文翻译 SettingsModel    │
│         ↑                                                     │
│  候选存储/统计 ← 过滤/证据校验 ← 项目候选提取服务             │
│                                                              │
│  上游翻译结果 → 项目术语合规验证 → 通过才提交 right.pdf       │
└───────────────────────────┬──────────────────────────────────┘
                            │ 受支持的 Settings/事件/输出契约
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ 未修改的 pdf2zh-next / BabelDOC                              │
│ PDF 解析、布局、字体、正文翻译、PDF 重建                      │
└──────────────────────────────────────────────────────────────┘
```

上游继续负责它擅长的 PDF 解析和排版；本项目负责它真正具有产品差异化价值的部分：用户术语决定、长期记忆、候选审核、约束验证和任务体验。

## 11. 每次开始新改进时给 AI 的任务模板

```markdown
请只处理术语改进清单中的 `<编号和标题>`。

要求：
1. 先完整阅读 `docs/improvement items/glossary-memory-improvement-plan-831.md` 的对应条目、前置条目和长期红线。
2. 同时阅读 `docs/project.md`、`docs/architecture.md` 以及与该编号直接相关的代码/测试。
3. 不实施其他编号，不顺手重构无关模块。
4. 绝对不要修改、fork、vendor、复制、Monkey-patch 或 import-shadow pdf2zh-next/BabelDOC；不要编辑 venv/site-packages。
5. 先增加能够证明当前风险或目标不变量的测试。
6. 实施满足本机、单用户、单活动文档、英文→中文边界的最小方案。
7. 用户定义/确认/锁定术语的优先级必须高于所有自动候选；候选未经用户接受不得进入正文有效词表。
8. 运行条目定向测试和 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1`，报告实际结果。
9. 如果当前架构事实改变，同步更新 `docs/architecture.md`；不要把未实现计划写成当前事实。
10. 只有全部验收标准满足，才把条目标记为“已完成”；部分满足只能标记“已改进”并记录剩余问题。
11. 最后列出修改文件、验证证据、未解决风险和对应提交；在本清单完成记录中追加一行。
```

建议用户在新会话中直接发送：

```text
请按照 docs/improvement items/glossary-memory-improvement-plan-831.md，只实施 P0-01。
```

完成并提交后，再把编号改成下一个满足依赖的条目。
