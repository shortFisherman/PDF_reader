> 本文档记录工程化、架构、可靠性和可维护性改进，不评价产品方向，也不自动授权一次性实施全部事项。
>
> 建立日期：2026-08-29  
> 审计基线：`0c98cd2`  
> 当前原则：保持本机、单用户、单文档、单体应用边界；优先消除数据损坏风险，再改善结构观感。

## 1. 如何使用这份清单

本清单是长期执行台账，不是要求一次性完成的重构计划。建议一次只处理一个编号，完成完整验证并提交后，再开始下一项。

每项使用以下状态：

- `待处理`：尚未开始。
- `进行中`：已经建立独立变更并正在实施。
- `已改进`：风险已降低，但尚未完全满足该项验收标准；必须补充“剩余问题”。
- `已完成`：全部验收标准满足，并记录了验证证据和完成提交。
- `暂缓`：当前明确不做，必须写明原因和重新评估条件。
- `不适用`：经核验后确认不适用于当前项目，必须写明依据。

更新条目时，不要只修改复选框。至少同时填写：

```markdown
- 状态：`已完成`
- 完成日期：YYYY-MM-DD
- 完成提交：`<commit>`
- 验证证据：`<执行过的命令、测试名称或报告路径>`
- 剩余问题：无 / <仍未解决的部分>
```

`已改进` 与 `已完成` 的区别：

- 如果只是加入前端按钮禁用、日志提醒或文档警告，而服务端仍可能违反正确性规则，只能标记为 `已改进`。
- 只有代码中的最终写入边界存在强制检查，并且有失败路径回归测试时，才能标记为 `已完成`。
- 测试数量增加不等于问题完成；测试必须覆盖该条目列出的验收场景。

## 2. 长期工程红线

无论未来如何重构，以下五条必须始终成立：

1. 一个翻译结果只能写回它开始时所属的文档。
2. 服务端同一时刻最多执行一个会修改文档状态的翻译任务，除非未来明确设计并验证了任务隔离。
3. 后台翻译线程或进程结束之前，其输入、输出和临时目录不能被提前删除。
4. PDF、术语表或阅读进度写入失败后，最后一个有效版本仍然可用。
5. 从干净环境克隆仓库后，可以安装依赖并运行统一验证。

如果任何改动可能破坏上述红线，应先补回归测试，再修改实现。

## 3. 执行纪律

每个条目建议采用同一流程：

1. 确认工作区干净，记录当前基线。
2. 为一个编号建立独立变更；不要把目录搬迁、行为修复和界面改版混在同一个提交中。
3. 先写能复现风险或表达不变量的测试。
4. 实施满足当前产品边界的最小修复。
5. 运行 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1`。
6. 涉及安装或依赖时，额外在全新虚拟环境中验证安装。
7. 更新 `docs/architecture.md` 中已经改变的事实。
8. 在本清单对应条目中记录状态、提交和证据。

禁止借清理之名顺手进行以下扩张：

- 不因为当前使用 Flask 就整体重写成 FastAPI。
- 不为了“专业”引入 Redis、Celery、消息队列、数据库或微服务。
- 不为了整理根目录而同时改写翻译流程。
- 不在没有真实需求和验收场景时设计多用户、租户或分布式任务系统。
- 不把原生前端整体重写成 React/Vue 作为工程健康修复。

### P0-01 翻译结果绑定不可变文档身份

- 状态：`已完成`
- 完成日期：2026-08-29
- 完成提交：`97b94e9`
- 验证证据：`tests/test_document_identity.py` 覆盖冻结快照、同路径重开换 ID、单页/批量迟到写回、迟到抽取、迟到术语合并与正常身份路径；`tests/test_translation_lifecycle.py` 验证迟到 PDF 被拒后不继续合并术语。执行 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1 -PythonExecutable "C:\Program Files\Python312\python.exe"`，208 个 Python 测试与全部前端测试通过。
- 剩余问题：无

#### 当前问题

`routes.py` 在翻译开始时创建调用 `state.replace_page()` / `state.replace_pages()` 的闭包。翻译期间若 `AppState.open_pdf()` 切换到另一文档，迟到结果会按新的 `_right_pdf_path` 和 `_right_doc` 写入当前文档。该风险已经在 `docs/architecture.md` 中记录并曾被复现，但尚无正式回归测试和运行时拒绝逻辑。

#### 目标状态

- 每次打开 PDF 都产生不可变的 `document_id` 或 `generation`。
- 翻译任务创建时捕获该身份，而不是结束时重新查询“当前文档”。
- 最终提交 API 必须接收 `expected_document_id`。
- 当前身份不匹配时，服务端拒绝提交、保留当前文档不变，并记录 stale-result 日志。
- 单页和批量翻译使用同一身份校验规则。

#### 建议实施步骤

1. 先写回归测试：文档 A 的任务尚未完成时打开文档 B，随后提交 A 的结果。
2. 在 `AppState` 中加入只增不减的 generation 或不可变 document session ID。
3. 提供锁内快照方法，返回任务所需的文档身份、哈希、页数和目标信息。
4. 将 `replace_page()` / `replace_pages()` 改为要求 `expected_document_id`。
5. 在写入前、持锁状态下执行最终身份比较。
6. 身份失效时返回领域错误，不得修改 PDF、翻译页集合或术语表。
7. 更新 `docs/architecture.md` 的状态模型和翻译链。

#### 验收标准

- [x] 自动化测试稳定复现旧风险，并在修复后通过。
- [x] A 的迟到结果不会改变 B 的 `right.pdf` 内容、页数或翻译页集合。
- [x] 单页和批量提交都验证文档身份。
- [x] 身份校验位于最终写入边界，而不只在前端或路由。
- [x] 完整验证通过。

- 状态：`已完成`
- 完成日期：2026-08-29
- 完成提交：`50f3844`
- 验证证据：`tests/test_translation_coordinator.py` 覆盖 16 线程同时竞争时恰好一个任务获准、幂等释放以及旧任务不能释放新任务；`tests/test_translation_routes.py` 使用两个 Flask 客户端验证单页任务占用期间批量请求返回稳定的 HTTP 409、拒绝路径不启动生成器且不创建临时目录、翻译期间 `/api/open` 不改变文档快照；`tests/test_sse_stream.py` 覆盖成功、上游错误、普通异常和消费者断开后的任务释放；前端测试验证 409 忙碌信息可见。执行 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1 -PythonExecutable "C:\Program Files\Python312\python.exe"`，222 个 Python 测试与全部前端测试通过。
- 剩余问题：无；后台 worker 的真实停止与临时目录所有权仍按 P1-01 单独处理，不属于本项互斥验收范围。

#### 当前问题

第二个浏览器标签页、页面刷新后的请求或直接 HTTP 调用都可以绕过前端 busy 标志。多个任务可能同时替换右侧 PDF、合并术语并操作共享状态。

#### 目标状态

在当前单用户产品边界下采用最小策略：服务端同时最多存在一个会修改文档状态的翻译任务。不要先实现队列。

建议引入一个很薄的 `TranslationCoordinator`：

```text
TranslationCoordinator
├─ active_job
├─ start(document_id, page_indices)
├─ finish(job_id)
├─ fail(job_id)
└─ is_busy
```

任务至少保存：

- `job_id`
- `document_id`
- 页码或页码范围
- 创建时间
- 当前状态
- 临时目录所有权（可在 P1-01 完成）

#### 建议实施步骤

1. 为两个客户端同时发起翻译编写路由级测试。
2. 增加线程安全的协调器，使用独立锁保护 active job。
3. 已有任务时，新翻译请求返回 HTTP 409 和稳定错误码。
4. 决定翻译期间 `/api/open` 的最小行为：优先返回 409；即使允许切换，也必须依赖 P0-01 丢弃旧结果。
5. 在成功、上游错误、普通异常和消费者断开路径上释放任务状态。
6. 前端根据 409 给出明确提示，但前端提示不能代替服务端互斥。

#### 验收标准

- [x] 两个并发翻译请求中只有一个被接受。
- [x] 被拒绝请求不会启动后台线程或创建翻译目录。
- [x] 成功和失败后 active job 都能释放。
- [x] 不会因异常永久卡在 busy 状态。
- [x] 每条翻译流程日志可以关联到 `job_id`。

#### 当前问题

#### 目标状态

- 所有修改在独立文档对象或临时副本上完成。
- 临时文件完整关闭后再原子替换正式文件。
- 只有磁盘提交成功后才替换内存文档句柄和 `_translated_pages`。
- 任意失败后，旧 `right.pdf` 仍可打开，`AppState` 仍可渲染。
- 所有 PyMuPDF 文档对象在所有异常路径上都关闭。

#### 验收标准

- [x] 分别注入 open、delete、insert、save、close、`os.replace` 失败并验证恢复。
- [x] 失败后旧 PDF 哈希或内容保持不变。
- [x] 失败后再次渲染和再次翻译可继续工作。
- [x] 单页和批量替换采用同一事务原则。

### P2-01 迁移为 `src/pdf_reader` 包布局

#### 是否值得做

值得，但目的不是“看起来更专业”。真正收益是：

- 明确哪些是生产代码，哪些是脚本、文档、测试和运行数据。
- 避免测试意外从仓库根目录导入源码，而不是从实际安装包导入。
- 支持 `python -m pdf_reader` 或正式 console script。
- 为相对导入、包资源、类型检查和未来发布建立稳定边界。
- 让根目录主要保留项目级配置和入口文件。

仅把 `.py` 文件机械移动到 `src/`，但继续修改 `sys.path`、依赖当前目录和使用裸模块导入，不会改善架构，反而会增加混乱。

#### 推荐目标结构

```text
PDF_reader/
├─ pyproject.toml
├─ README.md
├─ config.example.toml
├─ requirements.lock
├─ src/
│  └─ pdf_reader/
│     ├─ __init__.py
│     ├─ __main__.py
│     ├─ app.py
│     ├─ config.py
│     ├─ routes.py
│     ├─ state.py
│     ├─ sse_stream.py
│     ├─ translation_orchestrator.py
│     ├─ translation_lifecycle.py
│     ├─ translation_settings.py
│     ├─ engine_resolver.py
│     ├─ pdf_extraction.py
│     ├─ pdf_renderer.py
│     ├─ glossary_service.py
│     ├─ glossary_merger.py
│     ├─ logging_config.py
│     └─ debug_trace.py
├─ static/
├─ templates/
├─ tests/
├─ scripts/
└─ docs/
```

第一阶段可以继续把 `static/` 和 `templates/` 保留在根目录，通过 Flask 显式路径配置访问；不要强迫一次提交同时搬迁所有资源。等 Python 包迁移稳定后，再决定是否将资源放入包内。

#### 迁移前置条件

- P0-01、P0-02 和 P0-03 已完成。

#### 必须检查的破坏面

- `import config` 等裸导入要改为包内相对或绝对导入。
- 测试中的 `patch("translation_orchestrator...")` 等字符串路径必须更新。
- `Path(__file__).parent` 推导的 `config.toml`、`docs/glossary.csv`、日志和缓存路径会改变。
- Flask 默认查找 `templates/` 和 `static/` 的位置会改变。
- `python app.py`、`start.bat`、README 和 CI 启动命令要改变。
- CodeGraph、Ruff 的 per-file ignores 和测试收集路径需要更新。
- 调试日志、缓存和用户配置不能意外写入 `src/pdf_reader/`。

1. 引入 `pyproject.toml`、包名和可编辑安装，但不改业务行为。
2. 使用 `git mv` 移动 Python 模块并修复导入。
3. 增加 `__main__.py` 或 console script，更新启动脚本。
4. 显式修复配置、模板、静态资源、日志和缓存路径。
5. 更新测试 patch 路径、CI、Ruff、README 和架构文档。
6. 在干净环境安装并运行完整验证。

- [ ] `pip install -e .` 或确定的标准安装命令成功。

## 9. 关于根目录是否“不专业”的结论

根目录平铺 Python 文件不等于不专业。对于一个小型脚本应用，它甚至可能比多层目录更容易理解。当前真正的工程问题不是视觉上平铺，而是：

- 生产代码没有明确的可安装包边界；
- 导入依赖当前工作目录；
- 用户配置、模板、静态文件和源码路径耦合；
- 测试可能导入仓库里的源码，而不是验证安装后的程序。

当前看到的“根目录很乱”实际上混合了三类东西，应分别处理：

| 类别 | 例子 | 正确处理方式 |
|---|---|---|
| 生产源码 | `app.py`、`state.py`、`sse_stream.py` 等 | P2-01 中迁入可安装的 `src/pdf_reader/` 包，但应排在可靠性修复之后 |
| 项目基础设施 | `.github/`、`.comet/`、`.opencode/`、`openspec/`、`scripts/`、`docs/`、`tests/` | 不应为了根目录“空”而塞进 `src/`；应记录职责并删除确定不用的工具遗留 |
| 本地生成内容 | `venv/`、`node_modules/`、`cache/`、`logs/`、`__pycache__/`、`.pytest_cache/`、`.ruff_cache/` | 保持 Git 忽略，必要时由编辑器隐藏或使用安全清理脚本；它们不是源码架构的一部分 |

因此，`src/` 只能解决第一类问题，不能自动让整个项目根目录变得很空。像 `docs/`、`tests/`、`scripts/`、配置、锁文件和 CI 配置继续位于根层，本身就是正常的专业项目结构。

因此，迁移到 `src/pdf_reader/` 是值得做的中期工程工作，但它不能修复：

- 跨文档迟到结果污染；
- 并发任务覆盖；
- SSE 断开后的后台线程；
- PDF/术语写入事务问题；
- 依赖锁不可安装。

如果现在先搬目录，短期内根目录会更好看，但同时会改动几乎所有 Python import、测试 patch 路径、启动方式和资源路径，容易把真正的可靠性问题与迁移问题混在一起。正确顺序是：

```text
修复干净环境安装
  → 建立文档身份与单任务不变量
  → 明确任务资源所有权和写入事务
  → 固化系统级回归测试
  → 单独实施 src 包迁移
  → 再整理前端和工程卫生
```

完成 P2-01 后，根目录依然会保留 README、配置示例、锁文件、`docs/`、`tests/`、`scripts/`、`static/` 和 `templates/`；这是正常且专业的项目结构，不需要为了“空”而继续制造层级。
